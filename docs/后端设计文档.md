# Refer 高级参照 - 收藏与常用历史（后端设计文档）

## 1. 需求理解

本后端方案要解决 3 个核心问题：

1. 收藏是用户显式偏好，要求“实时可见、可取消、幂等可重试”；
2. 常用历史是高频行为数据，要求“低开销采集、可批量入库、最终一致”；
3. 前端列表查询必须沿用现有 refer 查询接口；
4. 允许新增 BFF 辅助接口（Top20 item_id 查询）用于拼装原查询条件。

为什么这样定义：

- 收藏操作频率低、交互强感知，实时写入收益高；
- 历史操作频率高，如果逐次写后端会放大 RT 和 QPS，采用“本地聚合后批同步”更稳；
- 统一读接口可避免前后端维护两套路由/鉴权/分页协议，降低长期维护成本。

---

## 2. 设计目标与非目标

## 2.1 设计目标

1. 主列表读接口不新增（沿用现有 refer 查询）；
2. 新增 BFF 辅助读接口（仅返回 Top20 item_id）；
3. 写接口清晰分离（收藏实时写、历史批量 sync）；
4. 全链路幂等（前端重试/网络抖动/重复提交不脏数据）；
5. 强租户隔离与用户隔离；
6. 达到评审级可运维标准（监控、告警、补偿）。

## 2.2 非目标（本期不做）

1. 组织共享收藏（scope 维度）；
2. 复杂推荐模型（仅规则分值）；
3. 历史实时流处理（本期为批同步）。

## 3. 架构设计（分层说明）

## 3.1 分层

1. Controller 层
   - 职责：参数校验、鉴权上下文注入、错误码映射。
2. Application Service 层
   - 职责：用例编排、事务边界、调用 Domain。
3. Domain 层
   - 职责：收藏幂等规则、历史聚合规则、分值策略。
4. Repository 层
   - 职责：SQL 执行、索引命中保障、批量 upsert。

## 3.2 为什么这样分层

1. 规则可测试：Domain 可单测，不依赖 DB；
2. 事务可控：Application 层统一定义 tx 边界；
3. 接口可演进：Controller 只做协议，业务变化不污染协议层；
4. 查询性能可持续优化：Repository 可独立演进 SQL。

## 5. 接口设计（评审级契约）

## 5.1 现有 refer 列表查询接口（保持不变）

主列表查询协议不做结构性改造（入参与出参与当前保持兼容），
收藏/常用历史页签通过 BFF 先拿 Top20 `item_id` 再拼接原条件。

## 5.2 BFF 辅助接口：收藏 Top20

- Method：`GET`
- Path：`/bff/refer/favorites/top20`
- Query：
  - `referKey: string` 必填
  - `keyword?: string` 可选
- Response：

```json
{
  "itemIds": ["000001", "000002"],
  "total": 2
}
```

语义：

1. 仅返回当前用户在当前 refer 下的收藏 Top20 条目 ID；
2. 用于 BFF 拼装原查询条件：`id in (...)`；
3. 不直接返回完整列表，避免与主列表协议重复。
4. 排序默认按 `updated_at desc`（最近收藏优先），取前 20 条。

实现核心逻辑（BFF）：

1. 校验 `referKey`；
2. 读取当前用户收藏表 `refer_user_favorite`：
   - where: `tenant_id`, `user_id`, `refer_key`, `is_deleted=0`
   - order by: `updated_at desc`
   - limit: `20`
3. 得到 `itemIds` 后，拼接到原 refer 查询条件：
   - `id in (:itemIds)`；
4. 调用原 refer 列表查询接口并原样返回分页结果。

## 5.3 BFF 辅助接口：常用历史 Top20

- Method：`GET`
- Path：`/bff/refer/history/top20`
- Query：
  - `referKey: string` 必填
  - `keyword?: string` 可选
- Response：

```json
{
  "itemIds": ["000003", "000001"],
  "total": 2
}
```

排序规则：

- 按需求图给定算法计算 score 并排序；
- 文档不重复定义公式细节，**以需求图算法为唯一准则**。

规则细化（按需求图落地）：

1. 时间切片
   - 只统计最近 N 天（默认 90，可配 180）；
   - 超过窗口的数据不参与主分，或按最低权重处理。
2. 最近优先（LRU 思想）
   - 越近的使用行为权重越高；
   - 昨天使用过的条目权重大于上月使用过的条目。
3. 示例加权（需求图示例）
   - 近 7 天使用过：`+10`
   - 近 30 天使用过：`+5`
   - 按总分排序取 Top20 进入常用列表。

实现核心逻辑（BFF）：

1. 从 `refer_user_history` 查询窗口内数据：
   - where: `tenant_id`, `user_id`, `refer_key`, `is_deleted=0`, `last_selected_at >= now()-N天`
2. 按需求图规则计算 `score`（若表内 score 已实时维护，可直接使用；否则按窗口重算）；
3. order by `score desc, last_selected_at desc`；
4. limit 20，返回 `itemIds`；
5. BFF 将 `itemIds` 拼接到原 refer 查询条件后调用原列表接口。

## 5.6 历史批同步

- Method：`POST`
- Path：`/api/refer/history/sync`
- 语义：按 `records` 批量 upsert，`selected_count += delta`

请求：

```json
{
  "referKey": "CustVendor.refer",
  "syncBatchId": "optional-batch-id",
  "records": [
    { "itemId": "000001", "itemCode": "000001", "itemName": "多多", "delta": 3, "lastSelectedAt": "2026-04-29T16:00:00Z" },
    { "itemId": "000002", "itemCode": "000002", "itemName": "信用（不开票）", "delta": 1, "lastSelectedAt": "2026-04-29T16:00:10Z" }
  ]
}
```

响应：

```json
{
  "successCount": 2,
  "failedCount": 0
}
```

实现核心逻辑（Service + Repository）：

1. 参数校验
   - `records` 非空、长度 <= 500；
   - 每条 `delta >= 1`、`itemId/itemName` 非空。
2. 事务处理（单请求单事务）
   - 按业务键查找历史行；
   - 不存在：插入 `selected_count = delta`；
   - 存在：`selected_count += delta`，`last_selected_at = max(...)`，重算 `score`。
3. 幂等处理
   - 若传 `syncBatchId`，先查幂等表/缓存，重复批次直接返回成功。
4. 返回批结果
   - `successCount`、`failedCount`，可选 `failedItems`。

## 6. 为什么是“本地批同步”而不是“每次提交直写”

1. 用户频繁选择时，直写会线性放大写请求；
2. 直写增加主流程尾延迟，对弹窗确认体验不友好；
3. 批同步支持压缩重复项（delta 累加），实际入库量显著下降；
4. 失败时可重试，不影响主业务提交（最终一致即可满足历史场景）。

---

## 6.1 为什么需要 BFF Top20 辅助接口

1. 主列表接口不改协议，风险最低；
2. Top20 查询与主查询解耦，便于独立优化；
3. BFF 可统一拼条件，前端实现简单且一致；
4. 算法在 BFF 集中实现，避免前后端重复实现偏差。

## 6.2 查询编排为什么放在 BFF

1. 原 refer 查询接口保持不变，避免影响存量调用方；
2. BFF 可做“Top20 获取 + 条件拼接 + 调原接口”聚合编排；
3. 安全边界更清晰：前端不直接拼接复杂条件；
4. 后续可在 BFF 增加缓存（如 Top20 30s 缓存）进一步降压。

## 7.3 字段级设计详解（评审重点）

## 7.3.1 收藏表字段说明与设计理由

1. 主键与业务键
   - `id`：数据库主键，便于内部引用与排障。
   - `tenant_id + user_id + refer_key + item_id`：业务唯一键，保证幂等。
   - 为什么：
     - 业务天然按“某用户在某参照下收藏某条目”唯一；
     - 比仅用 `id` 更能防止并发重复收藏。

2. 冗余字段
   - `item_code`, `item_name`, `item_snapshot`
   - 为什么：
     - 读接口可减少跨表/跨服务回查成本；
     - 目标对象主数据变化时，收藏列表仍可展示兜底信息。

3. 软删除字段
   - `is_deleted`
   - 为什么不用物理删除：
     - 取消收藏后再收藏可走“恢复”，减少写放大；
     - 保留变更轨迹，便于审计与问题追踪。

4. 时间字段
   - `created_at`, `updated_at`
   - 为什么：
     - 支持“最近收藏”排序扩展；
     - 支持数据归档与排障定位。

## 7.3.2 历史表字段说明与设计理由

1. 核心统计字段
   - `selected_count`：累计次数
   - `last_selected_at`：最近选择时间
   - `score`：排序分值
   - 为什么三者都保留：
     - `selected_count` 便于统计分析；
     - `last_selected_at` 便于时效判断；
     - `score` 便于直接排序，避免每次查询临时计算。

2. 幂等与合并字段
   - 业务键同收藏表
   - 为什么：
     - sync 批次是增量（delta）模型，必须能稳定落到同一行。

3. 冗余字段
   - `item_code`, `item_name`
   - 为什么：
     - 与收藏同理，提升展示链路稳定性；
     - 降低读链路依赖。

## 7.3.3 字段约束建议（落库规则）

1. 非空约束
   - `tenant_id`, `user_id`, `refer_key`, `item_id`, `item_name` 必填；
2. 取值约束
   - `selected_count >= 1`
   - `delta >= 1`（sync 入参校验）
3. 长度建议
   - `refer_key` 长度预留到 128，避免未来命名超长。

## 7.3.4 索引命中路径（按查询场景）

1. 收藏页签查询（BFF top20 + 主列表）
   - BFF 先查 top20 收藏 `item_id`；
   - 再拼接到原查询条件并调用主列表；
   - 依赖索引：`uk_tenant_user_refer_item`、`idx_tenant_user_refer`。

2. 历史页签查询（BFF top20 + 主列表）
   - BFF 按算法排序取 top20 `item_id`；
   - 再拼接到原查询条件并调用主列表；
   - 依赖索引：`idx_query_rank`。

3. 同步写入（history sync）
   - 按业务键查行后 upsert；
   - 依赖索引：`uk_tenant_user_refer_item`。

4. BFF 拼接原查询条件
   - 原条件：`criteriaStr + bindVars`
   - 附加条件：`AND id in (:id0,:id1,...,:id19)`
   - 若 `itemIds` 为空：附加 `AND 1=2`（快速空结果）

## 7.3.5 并发冲突与更新策略

1. 收藏并发点击
   - 依赖唯一键 + 幂等逻辑；
   - 冲突时按“已存在即成功”处理。

2. 历史批同步并发
   - 建议 update 使用原子累加：
     - `selected_count = selected_count + :delta`
     - `last_selected_at = GREATEST(last_selected_at, :lastSelectedAt)`
   - 避免读后写覆盖并发数据。

## 7.3.6 数据生命周期与归档建议

1. 收藏表
   - 默认长期保留（用户偏好数据）。

2. 历史表
   - 建议按“时间 + 分值”归档：
     - `last_selected_at > 180天` 且 `score < 阈值` 进入归档/清理。

3. 为什么要归档
   - 避免历史表无限膨胀；
   - 保持排序索引可控，稳定 P95。

## 7.3.7 迁移与兼容策略

1. DDL 先行发布，功能后开关；
2. 新字段对旧逻辑透明（旧接口可忽略扩展字段）；
3. 回滚策略：
   - 仅关闭新功能开关，不回滚表结构（避免二次风险）。

## 8. 核心流程与事务边界

## 8.1 收藏新增流程

1. 查业务键是否存在；
2. 不存在则插入；
3. 存在且 `is_deleted=1` 则恢复；
4. 存在且有效则直接成功（幂等）。

事务边界：单条写，单事务。

## 8.2 历史批同步流程

1. 校验 records（空、delta<=0、字段缺失）；
2. 以单批为事务执行 upsert；
3. 对每条记录：
   - `selected_count += delta`
   - `last_selected_at = max(db,lastSelectedAt)`
   - 重算 score；
4. 返回 success/failed 统计。

事务边界：单请求单事务（避免部分提交导致统计漂移）。

## 9. 幂等、重试与一致性

## 9.1 幂等策略

1. 收藏新增/取消天然幂等；
2. 历史同步建议使用 `syncBatchId`（可选但推荐）：
   - 相同 `syncBatchId` 重放不重复累计；
   - 解决网络重试导致重复加 delta 问题。

## 9.2 一致性策略

1. 收藏：强一致（实时写）；
2. 历史：最终一致（本地队列批同步）；
3. 查询：读取 DB 最终结果，不读取前端队列。

## 10. 安全设计

1. `tenantId/userId` 仅来自登录态，不信任前端透传；
2. 所有 SQL where 必带 `tenant_id` 和 `user_id`；
3. 写接口记录审计日志（who、referKey、itemId、action）；
4. 对 `records` 设置上限（如单批 <= 500）防止滥用。

---

## 11. 性能设计与容量估算

目标：

1. 主列表查询（favorite 场景）P95 < 150ms；
2. 主列表查询（history 场景）P95 < 200ms；
3. `POST /history/sync`（50 条）P95 < 250ms。

容量建议：

1. 同步接口单批推荐 20~100 条；
2. 超过阈值分片处理，避免单事务过大；
3. 历史冷数据按时间窗口归档（如 180 天）。

## 12. 错误码与失败处理建议

建议统一错误码（示例）：

- `REFER_FAVORITE_INVALID_PARAM`
- `REFER_FAVORITE_FORBIDDEN`
- `REFER_HISTORY_SYNC_INVALID_PARAM`
- `REFER_HISTORY_SYNC_TOO_LARGE`
- `REFER_HISTORY_SYNC_DUP_BATCH`

失败处理：

1. 参数错误：4xx，明确返回字段级错误；
2. 系统错误：5xx，前端保留队列重试；
3. 部分失败：返回 `failedCount` + 失败明细（可选）。
